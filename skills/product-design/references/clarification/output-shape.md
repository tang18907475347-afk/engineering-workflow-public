# 输出组织参考
> 什么时候拆 / 不拆按任务与可读性判断；本文只讲**决定之后文件具体长什么样**。

## 默认梯度
|情况|结构|
|---|---|
|简单需求|索引 + 1 个主体文件（`README.md + main.md`），低频细节折叠|
|常规|2–5 个模块文件|
|某模块过大|仍是**一个文件**：主链在外，低频细节折叠|
|出现干净接缝|才升级成「模块目录 + 主文档 + 细节片」|

推荐目录：

```text
.engineering/requirements/<req>/clarification/
├── README.md
├── <核心模块A>.md
├── <核心模块B>.md
├── shared.md        # 仅确有被多模块引用的共享定义时才生成
└── assets/          # 仅需要图片时生成
```

## 大文件先降扫读成本，别急着拆
文件偏大时优先让它可扫读，而不是分文件：

- **顶部「本页速览」+ 锚点目录**：3–5 行说清本文覆盖什么，配可跳转的 section 锚点，读者先判断是否深入。
- **低频细节用 `<details>` 折叠**：完整异常矩阵、字段级枚举、状态机全表、历史/旧稿说明等折进去。这是**默认手段、不是强依赖**——**主链必须在不展开任何折叠时完整可读**；viewer 不支持折叠时内容只是变长，不影响理解。
- **README 深链到 section**：索引不止链到文件，直接链到文件内小节，让读者跳到要看的那段——拆分后靠导航防碎。
- **共享上下文单点维护**：被多个文件引用的术语 / 状态 / 全局规则只写一处，其余链接过去，不每片复制前言。**但只有真的存在被多模块引用的共享定义时才抽 `shared.md`**；否则为防碎硬加一个 `shared.md`，本身就在制造碎片。
- **共用流程 ≠ 共享定义**：被两条以上链路引用的**共用流程**（如统一发布弹窗 + 审核链路 + 状态标签），若满足干净接缝（有独立读者、可独立读通）就独立成一个模块文件；`shared.md` 只放共享**定义**（术语 / 状态字典），不当共用流程的容器。

## README 示例骨架
```md
# 需求 × 交互澄清

## 范围

一句话说明需求目标、主要用户和本次覆盖范围。

## 模块

- [模块 A](./module-a.md)：一句话说明。
- [模块 B](./module-b.md)：一句话说明。

## 核心流程

入口 → 模块 A → 模块 B → 完成

## 关键风险与待决

真正会让产品 / 实现 / 用户体验分叉或受损的高价值问题；同一决策的重复症状合并，独立决策分开，没有就省略本节。**标题和「会发生什么」写外部可观察后果，不拿技术机制代替**；每条：

- **一句话风险标题（说清会出什么事，不用机制名）**
  - 会发生什么：用户会遇到、或业务会出的问题，非技术读者也看得懂。
  - 依据：资料里哪句、或哪两处相互冲突。
  - AI分析/建议：有足够依据时写推荐方向、理由和适用前提；依据不足时分析不同选择的后果，不强选。建议紧跟该问题，不得替代问题或自动结案。
  - 需要确认（确需拍板时）：写清产品 / 设计要决定什么；即使 AI 推荐了一个方向，实质分叉仍保留在问题清单。
  - 给研发（可选）：技术机制一句话；非技术读者可跳过。

## 其他资料差异与待确认

仅保留影响交付、又不能在正文消化的差异或缺失；纯表达或展示、且不改变用户或业务结果的低影响内容可合并说明。会造成实质分叉的差异留在「关键风险与待决」，不因 AI 建议而沉入正文。
```

## 模块文档示例骨架
```md
# 模块 A

## 目标

用户为什么来到这里、最终要完成什么。

## 核心流程

入口 → 用户操作 → 系统反馈 → 状态变化 → 结果 → 下一步

## 关键交互

### 场景 1

...

### 场景 2

...

## 异常与恢复

仅列真实存在且影响实现的失败、取消、重试、恢复。

## 关键风险与待决

真正会让产品 / 实现 / 用户体验分叉或受损的问题；没有就省略本节。每条写 会发生什么 / 依据 / AI分析或建议，确需拍板才写「需要确认」（技术机制放可选的「给研发」）；标题与「会发生什么」写外部可观察后果，不拿机制代替。AI 建议不能替代或关闭实质问题；建议尚未定案时，主流程不得按建议写成事实。

## 其他资料差异与待确认

只保留影响交付、又不能在正文消化的差异或缺失。
```

骨架是参考，不是固定 Schema。没有价值的章节应省略。
