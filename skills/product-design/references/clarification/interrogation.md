# 质询视角（按需取用，不是固定程序）
> 这是领域知识，不是每次 Product Design 都必须走完的流程。简单澄清可以只读资料、只处理一个明确歧义；复杂需求再用这些视角检查自己是否漏掉了会让产品、实现或体验分叉的地方。没有值得输出的问题就停，不设「至少找 N 个」的配额。

## 三个可切换的视角

### ① 产品语义
- 这个动作实际改变了什么？数据、状态、外部资源。
- 它和生命周期、依赖关系是否闭合？创建 → 生效 → 更新 → 失效，谁依赖谁，状态改动后是否都有明确归宿。
- 对于持续存在、可重复执行或会经历状态变化的核心行为：再次执行、处理中再次触发、规则 / 版本 / 审核标准后续变化，对已有对象和存量内容会发生什么？
- 中途失败、取消，或结果不明确后再次操作，会留下什么？例如创建审批单时自动生成的临时附件，取消后是保留、删除，还是转为可复用资源。
- 用户是否知道、并能控制重要或不可逆的变化？例如导入商品时系统自动规范标题或覆盖已有分类，用户能否看到、拒绝、恢复。

只追到足以判断业务后果的一层，不机械穷举次数。

### ② 实现后果
已明确写出的规则不是免检项。把涉及同一流程、对象或生命周期、却被分开写明的规则放到一起，判断它们组合后能否同时成立。

- 若组合会导致不同的用户结果、业务状态、重复操作、残留、不可逆后果，或需要产品拍板的决策分叉，就作为问题指出。
- 反过来，如果最终行为已经明确、只是实现起来复杂，那属于研发实现职责，不要升级成产品问题，也不要替研发设计技术方案。

### ③ 用户体验
站到用户位置走一遍，既看单点，也看整条路。

- 单点：单个交互哪里会困惑、丢失、被惩罚、失控或干等。
- 整条路：沿核心用户目标从入口到完成贯通走一次（全局走一遍即可，不逐页复述）。用户是否始终知道下一步；关键前置条件、限制、成本、不可逆后果是否在做决定前暴露；关键动作后能否知道发生了什么、当前处于什么状态；跨模块 / 跨页面后必要上下文是否连续；失败、取消、离开、误操作后有没有继续 / 恢复 / 退出出口；系统承诺「可在某处查看 / 继续 / 恢复」时，资料是否真给出了那条路径。

资料写了不等于对用户好。局部每一步都合理，整条路仍可能走不通——这类问题常常没有资料冲突。只指出用户损失，不挑视觉 / 文案审美毛病。

## 输出门槛
问题需有资料或现实依据，并能说明具体产品 / 用户 / 研发后果。真实歧义、冲突、关键缺口值得指出；语义已经明确但会造成用户损失的规则组合同样可以构成体验问题，不要求先找到多种解释。区分“现状有缺陷”与“目标未决定”，建议不自动成为已接受要求。

说明不了后果就不要为了「发现问题」而输出；不要优先找文案、视觉、低影响完整性问题。

## 写法
面向产品 / 设计 / 研发 / 测试混合读者。标题和「会发生什么」描述外部可观察的后果，不拿内部技术机制代替后果：

- 不好：「存在异步竞态」
- 好：「用户连点两次提交订单，可能生成两笔重复订单」

必要术语可以用，但机制不能替代后果；技术细节放进可选的「给研发」一行。存在明确合理选项时优先列 A / B，不为凑格式编选项。
