# 变更感知更新
已有澄清文档、产品资料又更新时，走 living documentation，不默认重新生成全部文档。

1. **检测变化**——经脚本采集的来源才重新采集，并用现有结果识别变化：PRD 看 `content_hash` 与 `history/` 的 diff stat（变化的章节标题）；Figma 的 `outline_hash` / `screenshot_hash` 变化只是内容变化线索：按需比较大纲、`get_screenshot.prev.png` 与新图，再判断语义影响，不按哈希变化自动重产。用户直接提供的文本、截图或说明则比较用户提供的新旧输入；旧输入不可得时，对照已有澄清内容，只说明能确认的变化，不声称存在来源级 diff。无实质变化就不重产。
2. **理解变化（模型）**——比较变化前后内容，判断产品语义具体变了什么。
3. **判断影响（模型）**——读现有澄清文档（通常 1–5 份），找出真正受影响的模块 / 段落。
4. **原地更新（模型）**——只改受影响内容，未受影响模块保持不变；变化若动了全局流程、模块边界或全局待确认事项，再同步 README（含增删模块）。

粒度是**模块文档级 + 文档内语义级编辑**，不是机器行级 patch，也不追求「精确改第几行」。不要为局部更新新建映射表、依赖图、traceability 或中间模型——「变化影响哪里」是语义判断，交给模型读 delta + 现有文档即可。
