# 问题定义的正反例
> **用来校准判断，不是模板。** 你的需求、领域和数据都不同；照抄这里的痛点或结构，本身就是一种失败。看的是差别在哪里。

**需求原文**（产品给的）：“优化项目发布流程，提升发布成功率。”
**背景**（来自 `context.md` 与 `reality.md`）：创作者在内容平台发布“项目”，提交后要经过内容审核；业务方关心“首次提交通过率”和“周发布量”。

---

## 反例：看起来完整，其实没抓住问题
```text
痛点：1. 发布按钮不够明显  2. 表单太长  3. 提交时 loading 不明显
方案：按钮改主色加大；表单分两组；加 loading 动画；每个字段加帮助说明
```
问题在哪：
- **没有业务定位**：不知道谁在用、业务要什么，就无法判断哪个问题重要。
- **痛点是想象出来的**：没有一条来自路径走查、数据或反馈。
- **没有聚焦**：四个改动平均用力。
- **没有根因**：发布成功率低的原因根本没被分析。
- **方案是换皮**：即使全部做完，审核拒绝率也不会变。

---

## 正例

**业务定位**
```text
谁：      每周发布 3–10 个项目的个人创作者
场景：    写完项目内容后提交发布，希望当天上线
要完成：  让项目一次通过审核并上线
现在：    提交 → 等待审核约 2 分钟 → 38% 被拒 → 只看到“内容不合规” → 逐个字段改了再试
业务要：  提高首次提交通过率（当前 62%），减少被拒后放弃（被拒后 45% 当天不再提交）
```
（数字来源：`context.md` §2，业务方提供的埋点数据）

**痛点与聚焦**（节选）
| 痛点（现象） | 证据 | 影响面×频率×严重程度 |
|---|---|---|
| 被拒后不知道哪个字段有问题，只能逐个改了重试 | `reality.md` §2 第 5 步；`ProjectEditPage#handleAuditError` 只能识别标题 | 2×3×3 |
| 等审核的 2 分钟里不能离开，离开后找不到结果 | `reality.md` §2 第 4 步；结果只靠当前页轮询 | 3×3×2 |
| 提交时才知道封面尺寸不对，要重新做图 | 客诉；尺寸只在后端校验 | 2×2×2 |
| 表单字段多 | PRD 提及；没有数据说明它影响发布（推断） | 3×3×1 |

本次重点：前两个，都直接关系到首次通过率与放弃率。
本次不解决：封面尺寸（单独排期做前端校验，不影响核心问题）；表单字段多（没有证据表明它导致失败）。

**根因**
```text
被拒后不知道改哪里 → 界面只显示“内容不合规” → 审核接口只返回一段文字，前端靠关键词猜字段
  根因：反馈——字段级的审核结果没有传到界面
等审核时不能离开 → 结果只靠当前页轮询 → 没有可以回来查看结果的地方，也没有通知
  根因：状态——离开页面后，这个任务的上下文就丢了
```

**确认点**
```text
出方案前，先确认我对问题的理解：
【业务定位】个人创作者要“一次通过审核并上线”；业务目标是首次通过率（62%）与被拒后放弃率（45%）。
【本次重点】1. 被拒后不知道改哪个字段 → 根因：审核结果没有细到字段
            2. 等审核时不能离开页面 → 根因：离开后任务状态丢失
【本次不解决】封面尺寸校验（单独排期）、表单字段多（没有证据）
【我不确定的】审核服务能否返回字段级结果？→ 建议：先问后端；不能的话，退一步按字段分别送审
```
确认之后，再进入目标体验与设计决定；那时的方案针对的是根因，而不是症状。

## 差别在哪
| | 反例 | 正例 |
|---|---|---|
| 从哪里开始 | 界面元素 | 谁要完成什么、业务要什么 |
| 痛点从哪来 | 想象 | 路径走查、数据、代码证据 |
| 重点 | 平均用力 | 聚焦两个，并说明不做什么 |
| 针对什么 | 症状 | 根因 |
| 人什么时候介入 | 方案做完之后才发现方向错了 | 出方案前花一分钟确认问题 |
