# 问题定义：一套可直接用的默认做法
> **这份文件为什么存在**：设计最常见的失败是解决错了问题——抓住表面症状、平均用力、没有业务视角。SKILL.md 规定了问题定义要达到什么（业务定位、带证据的痛点、聚焦、根因），这里给一套现成的做法。
> **什么时候可以不用**：你有能达到同样质量的做法时，直接用你的，在产出里说明即可。打分和分类是帮你思考的工具，不是要交付的表格；结论比形式重要。

## 1. 业务定位卡（五行）
```text
谁：      具体角色，不写笼统的“用户”
场景：    什么时候、为什么会来用
要完成：  他真正要完成的事，用“完成 X”表达，而不是“使用 Y 页面”
现在：    现在怎么完成的：多少步、多久、在哪里卡住
业务要：  业务方想要的结果，最好对应 context.md 里的指标
```
写不出某一行，就是该问的问题。

## 2. 找痛点的四个来源
1. **需求资料**：PRD、用户反馈里明确提到的问题。
2. **用户路径走查**：逐步看 `reality.md` 的「用户实际路径」，每一步问——
   - 这一步是多余的吗？本该系统做的事是不是让用户做了？
   - 用户是不是在重复输入、重复查找同一样东西？
   - 用户要等吗？等的时候知道进度吗？
   - 要做决定时，需要的信息就在眼前吗？
   - 出错了，用户知道原因、能恢复吗？
   - 用户要不要跳到别处，回来后上下文还在吗？
3. **历史问题**：`context.md` 的已知痛点、相关缺陷单、客诉。
4. **业务目标**：哪一步在拖累业务定位卡里写的那个结果？

## 3. 聚焦：一种打分方式
每个痛点按三项打 1–3 分，再相乘：

| 分 | 影响面 | 频率 | 严重程度 |
|---|---|---|---|
| 1 | 少数用户 | 偶尔 | 不方便 |
| 2 | 一部分用户 | 经常 | 浪费时间，或出错但能恢复 |
| 3 | 大部分用户 | 每次都会 | 丢数据、资损、放弃任务 |

- 分数要写依据；没有依据的分数标为推断，并在确认点里问。分数是排序的辅助，不是结论本身——依据比数字重要。
- 分数接近时，和业务目标直接相关的优先。
- 通常聚焦 1–3 个。真正存在一个系统性问题时可以只聚焦它，并说明为什么其他痛点是它的症状。
- 其余写进「本次不解决」，每条一句理由。

## 4. 追根因：一种分类方式
对每个重点痛点连续问“为什么”，通常 2–4 次，直到落到能做设计决策的一层：

| 根因类型 | 典型表现 |
|---|---|
| 流程 | 多余步骤、顺序不对、本该系统做的事让用户做 |
| 信息 | 做决定时缺信息，或信息不在需要它的地方 |
| 反馈 | 操作后不知道结果、进度或失败原因 |
| 状态 | 跨步骤 / 页面 / 会话丢失上下文，前后状态不一致 |
| 规则 | 业务规则冲突、不清楚，或不合理 |
| 结构 | 页面或模块按技术实现组织，而不是按用户要完成的事组织 |
| 能力 | 系统确实缺这项能力 |

分类帮助你确认“追到底了没有”，不是必须套进去的框。根因不属于任何一类时，直接写清楚它是什么。根因的 ownership 与 reach（本 surface、shared 资产还是系统级）按 [design-framework.md](design-framework.md) 判断：同一模式在多处出现，不等于存在共同根因。

## 5. 确认点消息的样子
```text
出方案前，先确认我对问题的理解（回复「确认」，或指出哪里不对）：
【业务定位】<两行>
【本次重点】1. <痛点>（依据：<一句话>）→ 根因：<一句话>
            2. …
【本次不解决】<痛点 a>（理由）、<痛点 b>（理由）
【我不确定的】<问题> → 建议：<你的建议>
```
