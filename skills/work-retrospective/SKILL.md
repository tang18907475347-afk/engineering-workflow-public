# Work Retrospective

## Runtime Contract
- **Outcome**：针对用户指定的范围，给出有证据指向的复盘：用户当时想要什么、哪里走偏或走反、原因落在哪一侧、可以怎么改。结论分三条出口交付：对插件、对用户的请求方式、对项目知识。
- **Done**：每条结论都带证据指针和把握程度；范围与数据缺口写在最前面；三条出口各有产出，或明确写“本次没有”。
- **Next consumer**：用户（决定采纳什么、是否保存报告、是否把某条写入 `.engineering/context.md`）；插件维护者（用户转交的案例候选）。
- **Stop**：只在用户主动要求时运行；不替用户采纳任何改动；默认不写任何文件（用户在复盘后明确要求保存报告，或要求把某一条写入 `.engineering/context.md` 时，才逐条执行）；不修改任何 skill 或插件文件；不把推断写成事实；没有证据的归因不写；不评判人，只描述事情是怎么走偏的。

## 为什么需要它
流程只会向前传：现状摘要传给设计，设计传给计划，计划传给实现和评审。结果好不好、哪里偏了，却没有路径送回上游。于是同样的偏差一遍遍重来，改进只能靠记忆和感觉。

有三个事实让这件事值得单独做：
1. **用户的每一次纠正、打断、重说，都是现成的“这里走偏了”的标注。** 不需要事后猜哪里错了，用户当时就说了。
2. **只看 agent 的轨迹，会得出“agent 做错了”，却看不出“要求本来就没说清”“目标中途变了”“验收口径一直没给”。** 走偏的原因常常不在 agent 一侧，也不一定在用户一侧，而在两者之间。
3. **逆向和澄清这类工作没有固定标准，也没有现成的最佳实践。** 标准只能从案例里一点点长出来，而且会被后来的案例推翻。这需要一个会积累、会修正的回路，而不是一次写死的规则。本 skill 只负责产出带证据的案例候选，积累由用户决定：保存哪些、并入哪里，由用户来定；skill 自己不存档、不建库。

## 它做什么，不做什么
做：把用户在某个范围内提出的要求，和之后实际发生的工作、最终的结果对起来看；找出偏离的地方，说清楚是什么偏离、可能为什么；把能改进的东西送回插件、用户和项目。

不做：不评分、不排名、不追究责任；不重新评审代码；不重做需求澄清或现状逆向（需要时指向对应的 skill）；不凭数据量不足的样本下统计结论。

## 范围是一个查询，不是一种模式
复盘的对象由用户说了算，不预设。可以是：
- 一个需求（`.engineering/requirements/<req>/`）、一个任务或一次会话；
- 一个分支或 MR；
- 一个时间窗口：上周、上个月、两个日期之间；
- 一个项目，或用一句话描述的事情（“上次改定价页的那一轮”）；
- 以上的任意组合。

用户没有说范围时，只问一次：想复盘哪件事或哪段时间？可以举例，不要替用户默认成“上周”或“最近一次”。范围的定义和片段的切法见 [references/scope-and-episodes.md](references/scope-and-episodes.md)。

## 证据从哪来，各有多可信
按需取用，哪层没有就说没有，用有的做，不用编的补：

| 层 | 是什么 | 能回答什么 |
|---|---|---|
| 项目产物 | `.engineering/requirements/<req>/` 下的现状摘要、澄清、设计决定、验收清单、提测与评审记录，`.engineering/context.md` 的纠偏记录 | 当时怎么理解的、定了什么 |
| 版本历史 | 分支、提交、MR、回滚、之后针对同一处的修复 | 实际交付了什么，之后有没有返工 |
| 会话记录 | 用户与 agent 的每一轮、工具调用与结果 | 用户说了什么、在哪里纠正、agent 做了什么 |
| 执行轨迹 | 耗时、token、报错、重试 | 哪里卡住、哪里反复 |

会话与轨迹不一定有、格式也不统一。本 skill 不绑定平台，也不自带采集器：按 [references/sources.md](references/sources.md) 的事件契约读取，事件流由用户或其 agent 提供。没有事件流时，只用项目产物与版本历史做复盘，并在报告开头写明“缺少会话记录，用户当时的纠正无法还原”。

证据可信度沿用共享契约的词汇：**OBSERVED**（已记录，记录里直接写了）、**DERIVED**（可推导，由记录必然推出）、**INFERRED**（推断，合理猜测，必须说明依据）。推断可以写，但不能当事实写，也不能悄悄升级成 OBSERVED。

## 怎么做（默认做法，可以重新组织）
1. **盘点。** 列出范围内有哪些数据、缺哪些，写在报告最前面。缺失本身就是一条结论，例如“本次没有会话记录，用户侧的判断只能从产物推断”。
2. **切片。** 以用户的每个要求为起点，到这个要求的结果落地为止，切成“请求片段”。一个要求可能跨多次会话，一次会话也可能含多个要求。
3. **找信号。** 在每个片段里找偏离的线索：用户纠正、重述、打断、拒绝；同一文件反复改、同一命令反复失败；回滚、之后的修复、验收被打回。信号只是线索，不等于结论。
4. **还原意图。** 用户明说的目标是什么，隐含的目标是什么，有哪些没说出口的约束。每一项标注依据档位。
5. **判定与归因。** 先判断是“偏”还是“反”（定义见 [references/taxonomy.md](references/taxonomy.md)），再归因到四侧之一或多侧：用户侧、agent 侧、插件侧、环境侧。归因必须能被反证：写清“如果当时有 X，这次就不会偏”。证据不够时写“无法判断”，这是合法结论；写不出反证的归因，只能作为“推断”列出并说明缺什么证据能确认或推翻，不作为结论。判断要按**当时已知的信息**来做，不用事后才知道的事去怪当时的选择。片段多的时候逐个片段标注，每次只带这一个片段的证据，避免相邻片段互相带偏。标注细则见 [references/annotation-guide.md](references/annotation-guide.md)。
6. **记下做对的。** 没走偏的片段、被一次说清的要求、被及时发现的问题，也要记。否则只能学到“避免什么”，学不到“保持什么”。
7. **汇总，走三条出口。**

允许结论是“这一段基本没走偏”。不要为了有产出而找问题。

## 三条出口
**A. 对插件。** 带证据的改动建议：哪个 skill、哪一处、为什么。只出一次的现象记为**案例候选**，不升级成规则；同类现象反复出现、根因清楚并有真实证据，才提议成默认做法（出现次数只是参考，不是门槛）。每条建议写明：依据哪几个片段、可能的副作用、如何回退、会不会限制强模型。只给建议，不改文件。

**B. 对用户。** 一面镜子：哪些请求方式之后更容易返工，哪些做法之后很顺。写成观察和可选项，不写成评价。例如“要求里没有验收口径的片段，有 N 个出现了第二轮纠正；开头补一句口径可以试试”。用户采不采用，由用户定。

**C. 对项目。** 建议写入 `.engineering/context.md` 的业务理解纠正，以及值得带到下一个需求里的假设，都只作为待确认条目列出，写与不写由用户决定。共享契约允许各 skill 写 `context.md`，不代表本 skill 会行使这个权限；模型推断的内容不写入。

产出的格式见 [references/outputs.md](references/outputs.md)。

## 判断自由
上面是默认做法，不是流程。强模型有更好的切片或归因方式时可以用，并在报告里说明。不可越过的只有三条：只在用户要求时运行；推断不当事实；不擅自写文件、不替用户采纳。

## 与其他 skill 的关系
独立运行。有其他 skill 的产物时读来当证据，没有时只用会话或只用版本历史也能做。不改写其他 skill 的产物，不为它们增加前置条件。发现需要重新逆向或重新澄清时，只指出，由用户决定是否调用对应 skill。

## 数据与读取
会话记录是用户自己的工作数据。本 skill 不主动上传到外部服务、不调用外部接口、默认不写入项目文件；但读取到的内容会进入当前模型的上下文，流向由所在的宿主和模型决定，不能假定“只在本机”。

默认做法（可以有更好的做法，说明即可）：读取前先告诉用户将访问哪些来源（目录 / 平台 / 时间范围）；范围大时先建索引、按片段取样，不一次读入全部会话；报告里用“证据指针 + 必要的短摘录”，不整段复制原文，也不带出密钥和令牌。
