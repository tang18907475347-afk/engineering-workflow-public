# 偏、反，与四侧归因
> 这是分类参考，不是必须逐项套用的清单。分类的目的是让“走偏”可以被比较、被累积，不是给事情贴标签。

## 偏与反
- **偏**：方向对，范围、程度或细节不对。例如：要求改一处文案，改了整页；要求加筛选，筛选做了但没有“清除”。
- **反**：结果与用户的意图相反或无关。例如：要求保留旧行为，却改掉了；要求只分析不改代码，却改了代码。
- **不算走偏**：用户自己改了主意、探索性的试错、双方都知道并接受的取舍。目标变了不是偏离，但“目标变了而没人说”是一条值得记的信息。

## 怎么发现偏离（线索，不是结论）
- 用户纠正：“不是这个意思”“我说的是……”“你再看看”“怎么没有……”，或直接给出正确答案。
- 用户重述：同一个要求换着说法再来一遍。
- 用户打断或拒绝：中断执行、拒绝批准、要求撤回。
- 用户感受不到：问“你改了什么”“我怎么没看出来”。这常常说明交付物与用户期待的可见度不一致。
- 返工的痕迹：同一文件反复修改、同一命令反复失败、回滚、合并后针对同一处的修复、提测或评审被打回。
- 用户长时间没回应后重新开始：只有在别处也找到“前面的内容没用上”的证据时才算线索，单独不能据此推断。

## 四侧归因
一次偏离可以有多个原因，可以同时落在几侧。每个归因都要写证据和把握。

### 用户侧
只描述“信息没有到位”，不描述“用户做错了”。
- 要求不完整：缺对象、缺范围、缺边界条件。
- 隐含约束没说出口：身份、职责、客户限制、风格偏好、之前踩过的坑。
- 验收口径缺失：没说怎样才算完成、完成后用户希望看到什么。
- 目标中途变化，且没有同步。
- 纠正滞后：问题出现很久后才被发现。

### agent 侧
- 误解：把要求读成了另一回事。
- 没问就做：存在明显分叉却自行选了一边。
- 把假设当事实：把推断写成结论，没有标注。
- 范围偏离：做多了、做少了。
- 上下文丢失：前面已经说过或已经纠正过的，后面又犯。
- 没有先核对现状就提议：不读现有内容就下结论。
- 重复同一类错误：说明问题不在这一次，而在默认行为。

### 插件侧
- skill 该触发没触发，或不该触发却触发。
- 指令之间冲突，或含糊到弱模型无从执行。
- 产物缺少下游需要的字段，下游只能重新问。
- 默认做法对弱模型太重，或对强模型成了限制（这条要特别留意：规则写得过死，会让强模型也只能做保守的事）。
- 插件的默认值与用户的真实意图相冲突，却没有给出可以跳过的出口。

### 环境侧
- 权限、工具不可用、网络受限、依赖缺失。
- 不包括数据缺失。没有会话记录、版本历史被清理、日志被截断，这些是“证据缺口”，写在报告的数据盘点里，不当作归因。

## 示例（来自一次真实对话，已泛化）
以下用来示范“证据 + 归因 + 反证”的写法，不是模板。

1. 用户说“你优化了啥？我咋没感觉出来呢”。
   - 偏离：交付的改进用户感知不到。
   - 归因：agent 侧（改的是需要先操作才出现的行为，没有问用户期待在哪里看到）；插件侧无证据。
   - 反证：如果交付时同时说明“怎么触发、会看到什么”，或把入口做得可见，这条纠正就不会出现。
2. 用户说“第一个说错了，我不是技术负责人”。
   - 偏离：对用户身份的假设错误，后续建议建立在错误前提上。
   - 归因：agent 侧（把推断当事实，没有标注）；用户侧（身份一直没有说明）。两侧都有。
   - 反证：如果开头把“我假设你是……”单独列出请用户确认，这一轮建议不会白做。
3. 用户说“你的回答太务实了，没有更具想象力的发散”。
   - 偏离：用户要发散，agent 一直在收敛。
   - 归因：agent 侧（默认收敛）；插件侧待查（现有的维护规则是否把强模型限制在保守做法上，需要读规则本身才能判断，此处证据不足）。
4. 用户说“看来是 agents 文档的内容把你的想法限制住了”。
   - 偏离：agent 的方案被既有约束框住。
   - 归因：插件侧（约束对强模型形成限制）。这是一条用户直接给出的归因，证据档位是 OBSERVED。
