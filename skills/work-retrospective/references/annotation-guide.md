# 标注细则
> 复盘的可信度取决于每条结论能不能被检查。本文规定怎么写，才能让用户一眼推翻你。

## 每条结论的最小结构
```text
片段：<编号>  范围内的哪个请求
观察：发生了什么（只写记录里有的）
证据：<来源 + 位置>  例：会话 s3 / 事件 e41；提交 a1b2c3；.engineering/requirements/x/plan.md「验收与保持」
档位：OBSERVED | DERIVED | INFERRED
判断：偏 | 反 | 未偏 | 无法判断
归因：用户侧 / agent 侧 / 插件侧 / 环境侧（可多个）及依据
反证：如果当时有 X，这次就不会发生（写不出反证时，只作为推断列出，写明缺什么证据能确认或推翻；不作为结论）
把握：高 | 中 | 低
```

## 证据指针
- 指向来源和位置，让读的人能回到原处。不要把大段原文搬进报告。
- 需要引用时只摘最短的能说明问题的一两句，并标明出处。
- 找不到证据，就写“没有证据”，不要用语气补。

## 三档可信度（沿用共享契约的证据词汇）
- **OBSERVED（已记录）**：记录里白纸黑字。例：用户说“不是这个意思”。
- **DERIVED（可推导）**：由几条已记录的事实必然推出，推导过程写出来。例：同一文件在 20 分钟内被改 5 次且每次都有同一个测试失败。
- **INFERRED（推断）**：合理但可能错。必须写依据，必须写什么会推翻它。报告的归因里推断占多时，一屏结论里要说明。

## 档位与把握
- **档位**说明证据本身有多直接：OBSERVED / DERIVED / INFERRED。
- **把握**说明这条结论有多可靠，由档位和反证共同决定：
  - 高：OBSERVED 或 DERIVED，且反证成立；
  - 中：证据档位足够但反证不完整，或 INFERRED 但有多条独立证据支持；
  - 低：主要依赖 INFERRED，或写不出反证。
- 档位是证据属性，把握是结论属性；不能只凭档位高就写把握高，还要看反证。

## 五条防线
1. **按当时已知的信息判断。** 事后才知道的事，不能拿来说当时的选择不对。要写成“如果当时知道 X”。
2. **区分“偏离”与“合理探索”。** 用户主动尝试、改主意、接受取舍，不算偏离。
3. **不把相关当原因。** 纠正发生在 agent 回复之后，不代表原因在 agent。读上下文，看用户纠正的究竟是什么。
4. **不为凑结论而归因。** 证据不够，写“无法判断”。
5. **同一个原因不要重复计数。** 同一个根因造成的几次纠正，合并成一条，写次数。

## 偏离的程度
只用来排序，不用来打分：
- 影响了交付结果或造成返工 > 影响了过程但结果无碍 > 只是表述上的小差异。
- 在“影响”一栏写具体后果，如“第二轮重写了三个文件”，不写“影响较大”。

## 写给谁看
读者是当事的用户，他最清楚上下文，所以：不解释他已知的事；把重点放在“没有注意到的模式”；归因里描写事情，不描写人。
