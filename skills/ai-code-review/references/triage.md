# Finding 验证与决策
本文件回答一件事：一条 AI 评审意见凭什么被相信、被修复、被关闭或被延期。它给的是判断依据，不是每次都必须跑完的检查清单；按 finding 的实际 claim 选择路径。

## 1. 一条 finding 由什么组成
`list_merge_request_ai_comments` 返回的评论通常包含：
|字段|用途|注意|
|---|---|---|
|`note` / `body`|评审正文，首行常有 `![缺陷 · 中](...)` badge|badge 只是云端分类|
|`path` / `line` / `lineRange`|评论落点|代码推进后可能失配|
|`notesCodeDiffContext`|评论对应的 diff hunk|是评审时的快照，不是当前代码|
|`context`|评审时的旧 / 新提交 SHA|与本地 HEAD 对比可发现代码已推进|
|`outdated`|评论是否已过时|只是提示，不是“已解决”|
|`suggestion`|建议 diff 与 `applied` 状态|建议可能已失效，不能盲套|
|`adopted` / `closed`|平台处理状态|不等于代码正确性|
|`parentNoteId`|是否为回复|AI finding 通常是顶层评论|

先读正文和 diff hunk，再读当前代码。不要只读 badge 就开始判断。

## 2. 按 claim 类型选择验证路径

### 缺陷（空值、边界、状态、错误处理、资源释放）
要回答：
- 评论声称的输入 / 状态在当前代码里是否可达？有没有前置守卫、类型约束、默认值、上游校验？
- 调用方是否已经保证条件？是否存在多条调用路径，其中一条绕过了守卫？
- 触发后坏在哪里？异常、错误数据、卡死、重复提交、资源泄漏，还是只是日志噪音？
- 是否本 MR 引入？用 diff 判断，不要用“文件里一直有”代替。

常见误判：
- 评论只看到函数内部的 `null` 分支，但调用方已经做了非空校验；
- 评论假设某个 API 会返回 `null`，但类型 / 契约 / 适配层已经归一化；
- 评论把测试代码、mock、dev-only 路径当成生产路径；
- 评论把“理论上可能”当成“实际可触发”，没有说明输入来源。

### 安全
不要接受“这里不安全”这种结论，要追完整链路：输入来源（用户 / 上游 / URL / 存储）→ 信任边界 → 校验 / 转义 / 鉴权 → sink（DOM / SQL / shell / 文件 / 网络 / 日志）→ 实际影响。

要确认：输入是否真的能到达 sink；现有校验是否覆盖该 sink 的语义；权限检查是否在正确的 owner 上；是否是本 MR 新引入的暴露面。只看到一个“危险 API”不足以判定漏洞。

### 性能
要看真实热路径和量级，而不是看到循环 / 大对象就报：
- 这段代码在什么频率下执行？首屏、每次输入、每次滚动，还是低频操作？
- 数据规模有多大？有没有分页、虚拟化、缓存、并发限制？
- 是否有可测指标（耗时、请求数、重渲染次数、内存）？没有测量时，结论强度只能是 `INFERRED`。
- 修复是否引入更大的复杂度或正确性风险？微优化通常不值得在本 MR 做。

### 可维护性 / 风格
先判断它是否违反**真实的工程约定**（项目 lint、目录 owner、公共组件契约、已有模式），还是只是评审者的偏好。
- 违反约定且会导致后续误用 / 重复实现 → 可以考虑修。
- 纯命名、格式、个人偏好、无关重构 → 默认 `DISMISSED` 或 `CONFIRMED + DEFER`，不要把风格意见升级成缺陷。
- 不要因为“改了更好看”扩大 MR。

### 测试
缺失测试本身不是缺陷，除非它覆盖的风险真实存在且当前没有其他证据：
- 该行为是否已有单元 / 集成 / E2E 覆盖？
- 缺失的测试是否针对本 MR 新引入的分支或回归风险？
- 如果补测试成本很低且能防止同类回归，可以修；否则说明现有验证边界，不要为了“测试覆盖率”制造形式测试。

## 3. 证据质量与边界
沿用共享契约的强度词汇：
- `OBSERVED` —— 本地实际读到 / 运行到 / 测到
- `DERIVED` —— 由已观察事实按明确规则推出
- `INFERRED` —— 合理猜测，尚未验证

- 源码存在只能证明 `implemented`，不能证明 `reachable` 或 `experienced`。
- 测试通过只能证明测试覆盖的那部分行为，不能证明所有入口。
- 负向结论必须写检查边界：搜了哪些目录 / symbol、排除了哪些调用路径、为什么可以断定不可达。
- 评论、工单、用户转述、其他 Agent 的结论都是待验证发现，不是证据本身。

## 4. 过期、建议与重复

### `outdated=true`
不要直接关闭。先在当前代码上确认：
- 原问题是否已经被后续提交修复？
- 代码是否只是移动 / 重命名，问题仍在？
- 行号是否失配，评论指的是旧实现？

如果当前代码已不再包含该问题，`DISMISSED`，理由写“当前代码已无该路径”并给出定位；如果问题仍在，按正常 finding 处理。

### `suggestion.diff`
建议 diff 是评审时的快照。应用前：
- 当前文件上下文是否仍匹配？
- 建议是否引用了已不存在的 symbol / 变量？
- 建议是否只修了症状，没有解决根因？

不匹配时不要硬套；可以按建议意图手写针对性修复，并在回复里说明差异。

### 同一根因的多条评论
同一文件 / 同一 owner 的多条评论可能指向同一个根因。处理方式：
- 本地按根因合并判断，修一次；
- 平台状态是 per-note 的，所以每条评论仍要分别反馈；
- 回复时引用同一个修复证据，不重复粘贴长文；
- 不要因为“已经有一条”就忽略其余评论的状态。

## 5. 严重性与修前判断：几个例子
|场景|云端标签|本地判断|修前建议|
|---|---|---|---|
|评论说某输入会为 `null`，但上游类型和运行时都保证非空|缺陷 · 高|不可触发，误报|`DISMISSED` + `SCENARIO_IMPOSSIBLE`|
|评论指出一个真实的空值分支，但只在 dev mock 中可达|缺陷 · 中|生产不可达，测试代码问题|`DISMISSED` 或 `CONFIRMED / DEFER`，说明边界|
|评论指出安全风险，但输入已经过白名单校验且 sink 不解析|安全 · 高|链路不成立|`DISMISSED` + 证据|
|评论指出一个低危但真实的边界错误，修复只需两行且有测试|缺陷 · 低|真实、便宜、可验证|`CONFIRMED` + `FIX` + proposal|
|评论要求把局部实现改成通用抽象|可维护性 · 低|偏好，且会扩大 scope|`DISMISSED` / `CONFIRMED / DEFER`|
|评论指出既有问题，本 MR 没有触碰该 owner|缺陷 · 中|真实但超出本 MR|`CONFIRMED / DEFER`，说明后续条件|

核心：**先判断事实，再判断价值，最后选择建议。** 不要让 badge 替你完成其中任何一步。

本地风险可以标为 `high / medium / low`，依据是影响面 × 触发概率 × 可检测性 / 可逆性 × 是否本 MR 引入。它用于决定处理价值，不写回平台的 severity，也不直接等于 assessment：高风险但不可触发仍然是 `DISMISSED`，低风险但真实且修复便宜仍然可以是 `CONFIRMED + FIX`。

## 6. Assessment 规则

### `CONFIRMED` + `FIX`
必须同时有：
- 当前代码确实存在评论声称的问题（或评论指出的风险在本地被证实）；
- 根因、影响与触发路径有本地证据；
- 给出建议 owner、改动方向、文件与验证要求；
- 如果根因不在当前可修范围、只做缓解，明确标注缓解边界，不把缓解写成根因修复。

修前不执行代码修改，也不自动提交平台 `adopt`。只有执行并验证后，执行报告才能写
`IMPLEMENTED` / `FIXED`；平台反馈是之后的独立动作。

### `CONFIRMED` + `DEFER`
问题真实，但当前不处理：
- 低优先级、已知问题、临时代码；
- 超出本 MR scope；
- 修复成本 / 风险明显高于收益；
- 需要后续需求或跨团队配合。

修前给出后续触发条件（例如“BFF 联调时删除 mock”），不要只写“以后再说”。
平台 `ignore` 不是自动动作；执行/处理后再按实际结果决定。

### `DISMISSED`
至少满足其一：
- 触发条件不可达，且有调用链 / 守卫 / 类型 / 运行证据；
- 评论基于错误文件、错误版本或对框架语义的误解；
- 当前代码已解决该问题；
- 建议不适用（语言 / 框架 / 场景不匹配）。

平台反馈可考虑 `reject` + 匹配的理由码，但必须在用户要求时单独提交；理由码只是分类，回复里仍要写具体证据。

### `NEEDS_EVIDENCE`
现有证据不足以判断，且继续猜会误导：
- 云端没有给出触发路径 / 输入 / 环境；
- 需要产品意图才能判断是否应该这样；
- 需要运行时数据、日志、截图或用户操作路径；
- 本地代码与评论版本差异过大，无法对齐。

修前不提交 `adopt/ignore/reject`；用回复提出**具体**问题（需要什么输入、哪条路径、哪个环境），保持 pending。拿到证据后重新判断。

## 7. 缺少 PRD 时怎么判断
技术性 finding 不需要 PRD：
- 空值 / 边界 / 类型 / 资源释放 / 错误处理；
- 安全链路、权限、注入、敏感信息；
- 性能量级、重复请求、渲染次数；
- 与当前 Repo 的既有契约冲突；
- 测试是否覆盖真实风险。

只有以下情况才需要产品上下文：
- “这个入口 / 按钮 / 提示是否应该存在”；
- “这个错误是否应该阻断流程”；
- “这个默认值 / 排序 / 权限是否符合产品预期”；
- “这个交互是否应该由前端还是后端负责”。

需要时按顺序找：当前 MR 描述 / 关联需求 → `.engineering/requirements/<req>/workspace/plan.md` 的「验收与保持」 → `.engineering/requirements/<req>/clarification/` → `.engineering/design/` → `.engineering/context.md` 的业务规则 → PRD / 设计稿 → 用户。找不到就标 `NEEDS_EVIDENCE` 或 `CONFIRMED + DEFER`，不要用“通常产品会……”补成事实。

## 8. 停止条件
出现以下情况时停止继续投入，交付当前结论：
- 已经能用证据闭合当前 finding；
- 云端重复同一观点且没有新证据；
- 修复需要跨模块方案、迁移、API 契约变更或产品决策；
- 本地代码与评论版本差异过大，继续对齐成本高于收益；
- 继续调查会变成全仓审计，而不是处理当前评审问题。

停止不是失败；把未闭合的原因、已拿到的证据和下一步需要什么写清楚，就是有效交付。
