# 修复与验证
本文件只回答：确认 finding 之后，如何修复到根因闭合，并用与风险匹配的证据证明它真的被修好了。它不规定固定测试清单；验证强度由 finding 的风险和 claim 决定。

修复以根因闭合为目标，变更范围由真实问题、行为契约和职责归属决定。允许局部修正，也允许结构性重构；改动规模不是质量标准。验证要充分覆盖本次变更的真实风险；只有在正确性得到满足后，才优化非必要复杂度和实施成本。

## 1. 修复前先确认边界
在动代码之前确认三件事：
1. **问题属于本 MR 吗？** 用评论的 diff hunk、`context` 提交与当前 diff 判断。既有问题若未被本 MR 触碰，默认不在当前 scope；只有安全 / 正确性风险且当前 MR 已触碰相关 owner 时才考虑一并修。
2. **修复会触碰谁？** 找到真正的 owner（状态写入者、公共组件、协议适配层、权限入口），不要在调用方打补丁掩盖 owner 的问题。如果正确修复需要调整 owner 或扩大范围，按当前任务已授权范围判断；不要为了保持 diff 小而留在错误 owner。
3. **有没有必须保留的行为？** 现有默认值、错误处理、空状态、权限、埋点、兼容分支是否会被改动影响？把不能破坏的行为先写下来。

如果边界不清楚，先回到 `triage.md` 判断，不要边改边猜。

## 2. 根因、Owner 与变更范围

修复以根因闭合为目标。允许局部修正，也允许结构性调整；选择依据是能否完整消除根因、是否正确归属职责，以及维护成本、复杂度和风险，而不是改动行数。

- 只改解决已确认 trigger 所需的行为；不顺手重构、不统一风格、不删除无关代码。变更范围由真实问题、行为契约和职责归属决定。
- 优先修根因：如果多个调用方都会遇到同一问题，修 owner；如果只有一条路径，修该路径。
- 两个方案都能恢复正确行为时，不以改动更小作为固定 tie-breaker；比较职责归属、长期维护成本、复杂度和风险。
- 不引入新的抽象层、配置项、开关或通用机制，除非根因、行为契约或现有代码要求这样做。
- 不复制粘贴大段逻辑来“绕过”问题；如果必须暂时绕过，写清原因、缓解边界和后续条件；缓解不写成根因修复。
- 保持现有 API / 数据结构 / 用户可见行为，除非 finding 本身要求改变它们；改变产品行为需要产品依据。

## 3. 验证强度
按 finding 的 claim 选择能证明它的充分证据，不是每次都跑全套；充分性由风险决定，至少覆盖触发路径、相邻回归面和失败路径：
|Claim|至少需要|
|---|---|
|空值 / 边界 / 状态错误|覆盖该分支的单元 / 集成测试，或可重放的运行时路径|
|错误处理 / 失败恢复|失败路径的测试或手动触发证据|
|安全 / 权限|可达链路证明 + 修复后该链路被阻断；必要时补回归测试|
|性能|修复前后可比较的指标（耗时 / 请求数 / 渲染次数 / 内存），或明确的复杂度论证|
|类型 / 编译|类型检查 / 构建通过|
|可维护性 / 风格|项目 lint / 约定检查；不需要伪造运行时证据|
|测试缺失|新增测试本身，以及它能失败于修复前、通过于修复后（可行时）|

验证顺序通常是：最贴近 claim 的类型 / lint / 单测 → 相关集成 / 组件测试 → 构建 → 必要时运行时 / 手动路径。不是强制流水线；如果最贴近 claim 的证据已经能证明 claim，就停。反过来，只有“构建通过”不能证明运行时行为正确。

## 4. 证据要可重放
记录：
- 执行的命令与关键输出；
- 覆盖的输入 / 状态 / 环境；
- 修改的文件与 symbol（不是只写“改了代码”）；
- 没有覆盖的部分和原因。

不要用以下内容冒充证据：
- “代码看起来没问题”；
- “类型检查过了” 来代替运行时行为；
- 实现者自述或提交说明；
- 一条无关测试通过；
- 删除 / 跳过失败测试。

## 5. 修复后的自检
- 重新读一遍原评论的 `path` / `lineRange`：代码位移后，回复是否还指向正确位置？
- 搜索是否还有同类调用路径未修；如果有，判断是同一根因还是独立问题。
- 检查修复是否引入新的空值、错误处理、权限或兼容问题。
- 如果新增了测试，确认它在修复前会失败（可行时），否则说明它只是防回归。
- 如果无法验证（缺环境 / 缺数据 / 缺依赖），执行结果不要写 `IMPLEMENTED` / `FIXED`；明确写“代码已改但未证明”，修前 assessment 仍保留 `NEEDS_EVIDENCE` 或说明缺口。

## 6. 什么时候不要修
出现以下情况时停下来，交回用户或上游：
- 修复依赖未确认的产品意图（入口是否应该存在、是否应该阻断、默认值应该是什么）；
- 需要跨模块重构、数据迁移、API 契约变更或权限模型调整，且超出当前任务已授权范围，或涉及实际权限 / 产品决定；
- 修复会改变其他团队 / 其他消费者的行为，当前 MR 没有相应授权；
- 问题真实但属于既有技术债，与本 MR 交付目标无关；
- 问题真实但不在当前任务交付范围，且可以安全延期；
- 本地 worktree 有未提交改动，修复可能覆盖用户工作。

停下来的输出仍然是有效结果：说明已确认的事实、为什么现在不修、建议的后续路径。

## 7. 提交与交付边界
- 可以在当前 worktree 修改代码、运行测试、查看 diff。
- 不自动 `git commit`、`git push`、创建 MR、合并或批准；只有用户明确要求才做。
- 不修改 `.gitignore`、CI 配置、发布配置或无关项目文件。
- 不把修复写成另一份持久化报告；最终结果放在对话交付里，平台反馈放在 MR 评论里。
- 如果用户要求提交，遵循仓库现有提交规范；提交信息说明修复了哪条评审问题，但不要把云端评论全文粘进去。

## 8. 与提测审查的交接
本 Skill 的验证只证明“这条 finding 的处理是否成立”，不等于整个 Requirement 达到提测条件。

如果用户接下来问“能不能提测”，交给 `test-readiness-review`，并让它独立读取：Clarification / Design（如有）、Workspace（如有）、Current Repo / Current Diff、本次修复与验证证据。

不要把本 Skill 的 `IMPLEMENTED` / `FIXED` 直接当成 `READY_FOR_TEST`；TRR 需要判断整个交付范围，而不是单条评审意见。
