# 回写通道
把终态结论写回缺陷单据。用户说自己改单据时跳过执行，只出草稿。

## 四动作（占位）
以下为调用格式示意：尖括号须替换为真实参数，含空格的路径须加引号。**本副本不含该脚本**——按同样参数语义实现你自己的回写入口，或直接用平台 API 完成等价动作。

```text
cd <目标项目的 Git worktree 根>
<回写入口> fixed <bugID> -m "已修复：一句话"                     # 状态→Fixed + 评论
<回写入口> fixed <bugID> --project-id <项目ID> --req-id <需求ID> --with-analysis  # 引用本需求档案摘要
<回写入口> assign <bugID> --to <负责人> -m "转派原因"            # 指派 + 评论
<回写入口> wontfix <bugID> -m "不修原因与证据"                   # 状态→Invalid + 评论（注：「设计如此/成本不匹配」关 Invalid 会计入 QA 误报统计，口径需区分时先与 QA 确认，再在客户端里分流 WONTFIX 状态映射）
<回写入口> comment <bugID> -m "追问/补充"                       # 仅评论
```

均支持 `--dry-run`（只打印将执行的命令，不落库）——先 dry-run 看一遍再真执行是低成本保险。自定义入口若没有此开关，先做一次只读查询确认将影响哪条单据。

fixed/assign/wontfix 必须带说明（-m 或 --with-analysis）：无说明的流转对验证人和接单人是黑箱，他们要靠考古评论区才能知道发生了什么。

`--with-analysis` 只读取确定需求的 dossier；省略 ID 时只接受已有需求档案的唯一命中，歧义时要求显式指定，不从 `_project/` 推断。

fixed 是两步非原子调用（改状态 + 评论）：中途失败时状态幂等可重跑，但评论会重复——重跑前先看状态是否已改，已改则只用 `comment` 补评论，不要整个重跑 fixed。写操作响应损坏时客户端应直接报错不重试（宁可人工重试，不可静默双写），这是接入新平台时必须继承的传输层纪律。

## 回写文案规范
三条规范，每条都有明确的失败代价：

1. **只谈本单**：不引用其他缺陷单（哪怕相关姊妹单）。读者是本单的验证人/相关方，跨单信息对他们是指令噪音；跨单关联只留在分析档案。
2. **两三句内**：结论 + 依据即可，不展开分析过程、不写方案细节——细节在档案里，想深读的人自然会去找。长评论文案的维护成本（谁改谁知道）远超信息增量。
3. **结论先行**：第一句就是处置结论（不修复/已修复/转派原因），依据紧随其后。验证人扫评论只花两秒，结论埋在第三句等于没写。

对照示例：

- 反例：「……引导已升级为字段标红+滚动聚焦（另一单 xxx）。如产品需……届时一并定义服务端校验口径与格式化空格上限。」——引了别的单、四句展开、混入需求定义细节
- 正例：「计数按原始字符（含空格）计算为行业通行口径，PRD 未对空格计数另作定义，属符合预期。如需空格不占额度，请提需求明确口径。」

## 质量兜底逻辑
回写后单据进入验证流程：验证不过 → Reopen → 下次拉取自动回队列（打回重修组，旧档案标过期重分析）。这意味着回写错了有结构性的纠错网——但代价是验证人一轮真机验证的时间。所以回写前的检查（多单元是否全实施、结论是否有据）值得认真做，回写本身不必反复犹豫。
