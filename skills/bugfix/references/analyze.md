# 分析通道
输入为已确定 `<req_id>/` 的队列卡片或用户描述；产物是 `<req_id>/analyses/<bug_id>.md`，供修复、pending 与回写消费。`_project/` 只供发现：选中缺陷后按缺陷 ID 在已有 my-bugs / pending / archive 快照中核实唯一归属；零命中或多命中先询问 `req_id`，不猜归属、不落档案。

## 调查与停止
从当前问题与可用证据选择调查方式，不固定 Probe、FAST / Heavy 路径、搜索次数、跳数或输入评分。简单问题因果已闭合就收口；复杂问题可继续追查实际会改变结论的分叉。依赖库或框架实现确实影响因果判断时，可以只读相关版本源码；定位在框架栈中本身不证明框架有缺陷，也不授权改 vendor / node_modules。

分析要解释 QA 触发路径如何产生 actual，区分预期与现状，并定位真实 owner。

**需求口径（有效期望）从哪里来**：能唯一对应到 `.engineering/requirements/<req>/` 时，优先引用该需求 Workspace「验收与保持」里的 `AC-n` / `P-n`（没有 Workspace、由设计直接完成的局部实现，看设计记录里的同名一节），在档案的「需求口径」行写上编号；对应不上或没有这一节时，照原方式用 PRD、设计稿与单据中的预期依据。`reality.md` 描述的是现状，不能当作期望。理解、触点、数据流、归类和影响面是可组合的领域视角，不是固定步骤。不要用分类、相似代码或附近存在某机制代替根因证据。

继续调查不能获得有判别力的新信息时，记录已确认事实、剩余分叉、缺失证据与可行下一步；暂定结论不冒充根因闭合。缺少 repo 外的产品预期、QA 环境或权限时具体提问，不先穷尽所有搜索，也不把可本地核查的事实转交用户。已有实现可说明现状，不自动成为产品期望。

两条观察看似冲突时，核对对象、版本、维度与触发条件；可通过源码、测试或 runtime 判别时继续核查。确实依赖用户 / 外部系统才停下询问。未验证的调和解释仍是假设，不能写成已确认结论。

## 恢复与 Reopen
已有档案且非 Reopen 时，先读头部完成度：
- 完成：批量采集 / 分析默认跳过；用户明确要求复查或新证据推翻时才重查相关部分。
- 暂定 / 待人工证据：批量刷新不自动重跑；新线索、证据或用户明确要求继续时，从记录的断点判断可用下一步，不充值搜索额度，也不重复无信息增量的尝试。
- 暂定·用户接受进修复：保留未闭环风险，不因用户接受就把证据改为完成；修复仍需当前明确授权与可执行方案。

续写合并为当前真相，保留有效事实、替换被推翻的结论；有续写时追加简短轨迹。回复不足以消除分叉时保持未决。续写完成仍停在分析通道，不自动修复。

Reopen 的旧结论已被现场否定：更新头部状态、追加二次分析，说明上次根因、归属、方案或验证具体哪里失效。保留这一故障依据，不强制重做未受影响调查。

## 证据与定位知识
媒体在文字无法说明 actual、视觉差异本身是问题、顺序重要、或能区分候选根因时使用。视频可先查时长再抽关键帧；不可辨就如实记录，不编造帧证据。

卡片带日志引用时可直接读取原始快照；采集失败可用 `<日志平台> dump <logId>`（占位，本副本不含该脚本）重试：
- `sourceMap.originalFile:originalLine` 与 `codeContext` 提供源码锚点，需核对本地版本。
- 错误消息与配置 / 状态字段是根因线索；页面 URL 与 query 是复现条件；构建号可辅助反查 commit。
- 错误指纹不等于完整行为链；复现意图与路径仍需卡片等证据。

`debug` 字段仅合法 `debug-report-{uuid}` 可消费；页面名、路由名等值标注不可用，不据此盲查。

性能问题需要能支持所声称因果的运行数据，不从静态嫌疑直接定罪。机型差异可按 model 分组比较首屏指标的加权均值；聚合相关性仍不等于具体因果，必要时 profiling。验证依据是目标指标、环境和观测，不因“体验”类别就宣判只能人工。

按单查询 `<project>/<req_id>/code-index.md` 可缩短 QA 业务词到代码的翻译；跨单命中只作候选，以当前 Repo 核验。高恢复成本、跨文件且可复用的工程事实可按需查 `.engineering/intelligence/`；简单查找直接读源码。缓存不预置根因；失效内容按 [代码机制缓存契约](../../product-reality/references/code/intelligence-contract.md) 修正或删除，不要求每单加载或回流。

外部资料使用当前宿主已有授权能力：需求文档、设计稿、本地测试资料各走宿主提供的通道。持久证据放 `<project>/evidence/`：文档 / 设计按来源 URL 短哈希命名复用，日志使用 `log-{logId}-raw.json`。同源复用前考虑是否已更新；缓存命中不是永远新鲜。本地资料需要稳定引用时复制入池，不引用临时文件。

## 缺陷性质、归属与影响
多个现象可能同源，也可能是独立缺陷单元；只有必要时拆内部单元，不拆外部单据。整单 Fixed 要覆盖约定复现路径，不能用修好其中一半代替完整结果。

分类只提供诊断线索，不产生修复许可或自动化等级：
|类|名称|判定特征|典型根因|
|---|---|---|---|
|A|需求变更残留|需求说砍了界面还在 / 数据恒空仍渲染空态|触点枚举缺失|
|B|状态残留|切换/重开后首帧闪旧数据，或残留上次会话的校验/交互状态|常驻挂载组件重置链路遗漏|
|C|竞态|偶现、快速操作触发、时序相关|异步响应无活跃态校验|
|D|空态泄露|「暂无X」出现在不该出现的场景|空态渲染与业务状态未联动|
|E|交互时序|Esc/焦点/快捷键相关；限长输入「新输入替换已有文本」|事件冒泡/注册清理缺失；全局拦截器+硬编码转发清单（新增浮层必漏——查拦截清单与浮层集合的差集）；受控限长输入缺 IME 组合守卫（组合期截断回写打断输入法 + slice 头部保留在中间插入时吃旧文尾部）|
|F|接口/服务端|前端零嫌疑、接口报错或数据错|后端问题，转派|
|G|纯样式|像素/间距/重叠|token 误用或布局约束冲突|
|H|性能/体验|慢/卡/白屏/帧率，常带机型或环境特异性（如某机型慢、其他机型正常）|主包膨胀（大页面静态 import 而非 lazy 分 chunk）/ 长任务阻塞主线程 / 无谓串行请求；需按实际性能指标与运行环境验证，不由归类直接定罪|


常见调查线索：状态残留可比较会变化的 state 与实际重置集合；空态泄露需区分数据恒空与尚未加载；竞态关注异步结果的活跃态；新引入问题可用 git history 找行为变化，不要求每单查历史。交互 / 样式问题关注真正渲染宿主、伪类覆盖与 IME 等实际事件语义，不把 DOM 属性绿灯当成视觉结果。

归属按因果独立判断：
- **前端修复**：根因与可执行修改在前端，说明真实接口、设计或需求前置是否阻塞。
- **后端修复**：根因在接口行为，附响应、诊断或链路证据与置信度；推演未确认时写待后端确认。
- **不修复**：有依据证明符合有效期望、真实技术限制或用户接受的取舍。行业惯例可辅助比较，不能替代本产品授权。
- **待需求确认**：产品预期 / 方案确实未决时说明分叉；不能为填“怎么修”而发明默认行为。

共享触点需调查实际消费者和行为变化；检索所得集合不自动等于全集。影响范围关注哪些现有行为会变、哪些回归需保护，不由文件数机械定档，也不自动扩展到整个交互域的所有历史问题。

## 档位与验证边界
档位保留给修复通道使用，反映当前可执行性，不替代证据判断：
|档位|含义|
|---|---|
|全自动|当前授权与已确认方案内，Agent 有条件完成实现及所需验证|
|半自动|可实施，但存在明确需人工 / 外部环境完成的验证或审阅义务；写出具体缺口|
|手动|必要产品决定、依赖、因果或方案尚未成立，当前不能安全执行；说明阻塞原因|

以实际可获得证据判断覆盖：unit、DOM、browser、截图、真实环境均可有自动化能力，也都有覆盖边界。mock 只证明被模拟的行为；已验证的浏览器视觉结果不因属于“视觉”就自动转人工。人工义务来自实际未覆盖的重要结果或用户要求，不来自固定 L1–L5 层表。方案与环境变化时可重判档位和验证策略，记录依据，不照搬失效判断。

档位不授予 commit 或外部单据写权限；分析落档即停，修复、提交与回写分别按用户点名的通道执行。

## Dossier 机器消费契约
以下头部、节序、粗体归属、编号修复与档位行是 pending / 修复通道的实际接口，保留稳定；其他内容按需要写，不固定解释长度或证据数量。已确认事实与方案分开，未知明确保留。

```markdown
# {bug_id} Bugfix 分析档案

> 状态：{New/Open/Reopen…} · {完成度} · {日期} · 快照 commit：{hash} · 类型：{归类或本地单}
> 标题：{缺陷标题原文}
> 需求口径：{有效期望；无法确认写 UNKNOWN}

## 结论
**{前端修复｜后端修复｜不修复｜待需求确认}**：{定位概括}
- **根因**：{触发路径与机制；未闭合如实说明}
- **修复原则**：{已确认方案或待决分叉}
- **改动范围**：{文件与受影响消费者}
- **档位**：{全自动｜半自动｜手动}（{实际依据}）
- **验证边界**：{已能证明什么；仍需什么证据}

## 根因
{现象、相关状态 / 调用链与因果依据；文件 + 符号 / 行，必要代码片段与版本边界}

## 修复
1. {具体文件 / 模块：从什么行为改为什么，为什么；未决时明确待确认，不伪造可执行方案}
2. {与目标行为匹配的验证方式及条件}

## 影响范围
{实际变更、API / 数据结构影响、关键 Preserve 与调查边界}

## 风险与验证

## 执行结果
尚未执行。
```

完成度沿用：完成｜暂定（PROVISIONAL·原因）｜待人工证据（ASK·待答问题）｜暂定·用户接受进修复。只有真正续写时增加“续写轨迹”，规则确实升维时可用“约束沉淀”留指针，不复制规则正文。

档案落盘后执行两步（均为占位，本副本不含脚本）：
1. `<档案校验> <bug_id> --req-id <需求ID>`，FAIL 修正后再继续；WARN 不阻塞。
2. `<本地同步> --req-id <需求ID> --bug-id <bugID>`，本地同步，不自动发起平台写入。

## 知识出口
业务词典仅存本需求语境的 QA 同义词 → 完整路径 + 可检索符号；翻译成本明显、新映射或失效锚点时才更新，同单同义词归一。根因、修法与调查过程留档案，避免下次预置旧结论。脱离需求仍成立的昂贵代码事实按代码机制缓存准入处理，不批量迁移旧词条。

不每单主动沉淀技能规则。Reopen / 验证证明旧规则错误、同类 failure 重复或发现已验证且非显然的可复用规律，并能指出实际消费位置时，才修正现有 reference；案例细节、缺陷 ID 与项目专属解法不进入通用规则。收编已有知识而非另建登记表，流程 / 架构提案不自动执行。

确有可独立调查或验证的工作且宿主允许委派时，可参考 [subagents.md](subagents.md)；返回的因果假设仍需结合当前证据核验。
