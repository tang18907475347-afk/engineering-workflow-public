# 采集通道
拉取需求范围的缺陷清洗成三文档；`--scope project` 只写 `_project/my-bugs.md` 发现队列，不维护项目级 pending / archive。这一层只出客观数据——不读业务代码、不做路由到源码的映射、不下根因判断。原因：采集层一旦掺入解读，后续分析会被自己的预判锚定（先入为主比无信息更难纠偏）。

## 采集入口（占位）
以下为调用格式示意：尖括号须替换为真实参数，方括号表示可选项（执行时去掉括号或整个选项），含空格的路径须加引号。**本副本不含这些脚本**——按同样参数语义实现你自己的采集入口，或直接用平台 API / MCP 完成等价动作。首次列表采集须显式提供项目 ID；已有唯一项目配置时才可省略。

```text
cd <目标项目的 Git worktree 根>
<列表采集> --project-id <项目ID> --req-id <需求ID>   # 首次按需求采集；后续唯一项目/快照可省略相应 ID
<列表采集> --project-id <项目ID> --scope project     # 项目级发现队列，仅 my-bugs.md
<列表采集> --detail <bugID> [--project-id X]         # 单条速查（URL 入口；project_id 缺省读 config，无则跳过媒体下载）
<列表采集> --owner <负责人>                           # 查他人名下（默认 whoami 自己）
<列表采集> --no-media                                # 不下载媒体
<列表采集> --format json                             # 结构化 stdout（供程序消费）
```

显式传参的持久化只存项目层字段（--project-id 登记项目、--app-id 存监控 appId）；需求不进 config——平级无「当前」概念，缺省解析用项目快照目录唯一推导，多个须显式 --req-id。单单 URL 解析出的 project_id 同样走登记反哺。

数据层按平台拆分是本 Skill 的既有教训：平台客户端共用层负责命令执行与输出净化（命令回显截取、ANSI/进度条净化、未转义控制字符、裸数字键加引号、大输出偶发损坏重试），业务层只放单据语义，日志层只放日志语义。**绕开封装直接拼平台命令等于把这些坑全部重踩一遍**——这是接入新平台时唯一必须继承的部分。

平台客户端接口（参数/子命令/文件名）变更后，同步更新本目录文档——接口演进而文档留尾巴是最常见的失效来源。

## 需求快照的三文档状态机
输入三个信号：单据活跃性 × 档案存在性 × 档案新鲜度（档案头「状态」）。

|单据状态|档案|档案头状态|去向|
|---|---|---|---|
|New/Open|无|—|🟡 my-bugs.md 待分诊|
|New/Open|有|New/Open|🔵 pending.md（待拍板）|
|Reopen|有|Reopen|🔵 pending.md（本轮已重分析）|
|Reopen|无/有|—/New/Open|🔴 my-bugs.md 打回重修，卡片头标「有旧档案」|
|Fixed|有|—|🗄️ archive.md（档案永不删，与「离开活跃列表」同路）|
|Fixed|无|—|不进任何文件（被打回自动回 Reopen 队列）|
|离开活跃列表|有|—|🗄️ archive.md 一行一单|

设计意图：需求快照的三文档均为每次拉取的派生视图，唯一持久分析状态源是本需求 `<req_id>/analyses/` 目录本身（文件存在即已分析）——不建分析状态索引、不做事件日志、不存手工标记。持久状态越少，状态不一致的空间越小。需求通道经平台侧拉取过滤（`--status pending`，New/Open/Reopen），实际看不到 Fixed；Fixed 档案由本需求归档派生收录，不扫描项目级或其他需求档案。分析完成不用等下次需求拉取：本地同步入口只对已确定 `req_id` 的需求快照按同一状态机即时路由进 pending（零网络本地同步，拉取结果永远覆盖本地终态一致）。项目范围含 Fixed，但只供发现，不进入此状态机。

从 `_project/my-bugs.md` 选中缺陷时，先在已有各 `<req_id>/` 的 my-bugs/pending/archive 快照中按缺陷 ID 精确核实归属；只接受唯一命中，零命中或多命中就询问用户 `req_id`。确定后若需求快照尚不存在，先按该 `req_id` 拉取一次；Fixed 缺陷可能不在需求活跃列表，用项目发现卡片或 `--detail` 作为单据输入。随后进入该需求快照的分析与同步链，不从 `_project/` 直接分析或生成项目级 dossier / pending / archive / code-index。旧的项目级 analyses/pending/archive 若存在，不作为当前状态读取，由用户人工整理；不做自动迁移。

Reopen 重分析时在旧档案**追加**「二次分析」节并更新档案头状态，不静默覆盖——打回原因和历史判断都是信息，覆盖等于丢证据。

## 卡片协议（my-bugs.md，Agent 解析契约）
```markdown
## 🟡 待分诊（N）                     ← 仅非空组渲染（🔴 打回重修同构）
### {id} · {优先级} · {状态} · {标题}   ← 卡片头四段「 · 」分隔（Reopen 有旧档案时追加标记）
- 类型：{标签} ｜ {业务模块} ｜ {环境}   ← 固定行序，有值才出现
- 路由：{page 路由}                     类型 → 路由 → 信号 → 预期依据 → 验证人/创建
- 信号：{偶现｜必现} ｜ {长期存在｜疑似新引入}       → debug → 媒体索引 → 预期 → 实际 → 步骤 → 增量正文
- 预期依据：{PRD/设计稿/竞品关键词}
- 验证人：{名} ｜ 创建：{MM-DD HH:mm}
- debug：{debug-report id}               ← 原样透传，不做存在性判定（消费判定在 analyze.md：非 debug-report-{uuid} 形态标「不可用」走常规路径）
- 日志：[{短码 8 位}](../evidence/log-{完整id}-raw.json)   ← 正文/评论里的日志链接自动提取并拉取落盘（不清洗原始 JSON；失败降级仅展示 id 供分析时重试）
- 媒体：图1={文件} ｜ 视频1={文件}
- 预期：…
![图](../media/…) / 🎬 [video.mp4](../media/…)
- 评论：N 条                          ← N=0 整块不存在
> {作者} · {时间} / > {内容多行}       ← 时序时间线
```

解析契约：key 行以全角「：」分隔；一行内多字段以「 ｜ 」分隔；**行不存在即无值**（采集层有意用「缺席」表达「无信息」，避免占位噪音）。pending.md 条目 = 卡片头 + ⏸ 完成度行（仅暂定/待人工证据态出现——等待外部输入的稳态标记）+ 归属/方案/档案行；archive.md 一行一单。

## 清洗规则
每条规则都在回答同一个问题：分析 Agent 读卡片时，哪些信息是信号、哪些是噪音？

- **丢弃零信息字段**：问题来源（恒「手工发现」）、创建人/提交渠道——恒定值不构成区分度
- **占位值不渲染**：「无」「详见图片」「详见视频」「详见录屏」——媒体正文已内嵌，占位文字是重复
- **正文句级去重**：描述句子被标题覆盖则丢弃——标题是分析的第一输入，重复句只会稀释注意力
- **URL 净化**：剥部署灰度参数（`_fea_tag`/`_force_update`），只留路由
- **状态过滤**：需求通道平台侧 `--status pending`（New/Open/Reopen）；项目发现队列含 New/Open/Reopen/Fixed，不按分析状态分流
- **评论全文直出**：打回原因/转派理由/验证讨论都在评论里，是分析的高价值输入——给链接二次导航就失去了汇总的意义
- **媒体本地化**：带签名 URL 的附件下载到 media/（幂等缓存），图内嵌可预览、视频文件链接；失败退回 URL 并标注
- **信号提取**：模板无专用字段，从全文关键词预判复现频率（偶现/必现）、回归边界（长期存在/疑似新引入）、预期依据（PRD/设计稿/竞品提及）——有信号才渲染。这是分析分流的第一依据：偶现优先按竞态查、新引入优先按回归查引入 commit、无预期依据优先追问依据

## QA 模板反馈（输入质量治理）
三个字段建议反馈给测试团队加入缺陷模板——一次模板改动所有后续单据受益，比 Agent 逐单追问便宜得多：

|建议字段|为什么值这个钱|
|---|---|
|回归边界（上次正常的版本/日期）|把全代码库搜索降维成单 commit 范围搜索，性价比最高的定位加速器|
|复现频率（必现/偶现+概率）|确定性缺陷 vs 竞态的第一分流，偶现无此信息只能读代码想象|
|预期依据（PRD 条款/设计稿/竞品）|预期本身可主观，依据才可判——光有预期没有依据会被带偏|

反馈前的过渡期靠信号提取 + 分析通道证据增强兼着扛。
