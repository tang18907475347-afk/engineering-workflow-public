# Bugfix

## Runtime Contract
- **Outcome**：完成用户点名的缺陷通道并产出对应快照、分析档案、修复或回写结果。
- **Done**：该通道要求的落盘、校验或确认条件已满足。
- **Next consumer**：用户；分析档案只在用户继续授权后交给 Fix 或 Triage。
- **Stop**：严格停在用户点名的通道，不自动转入修复、提交或工单回写。

被指派人视角的缺陷处理能力集。四个能力并列：**采集 / 分析 / 修复 / 回写**——它们是四条独立通道而非流水线，用户的意图决定走哪条，走完即停。

## 平台适配（本副本不内置客户端）
本 Skill 只沉淀流程与判断，**不携带任何缺陷平台客户端脚本**。原实现依赖的专有 CLI、单据系统与日志平台均已移除；下列位置是显式占位，接入时按你自己的平台替换：

|占位|需要你自己提供的|
|---|---|
|`<缺陷平台客户端>`|读写单据、评论、状态流转的命令行或 API 封装（认证由它承担）|
|`<列表采集>`|按项目 / 需求作用域拉取被指派人缺陷列表的入口|
|`<日志平台>`|从报错链接提取调用栈、构建号与页面参数的入口|
|`<档案校验>`|分析档案格式硬校验脚本（可省，退化为人工核对节序）|

占位命令在文中以 `python3 <本 Skill 所在目录>/scripts/<脚本>` 形式示意调用形状与参数语义；**文件不存在是预期的**，按接口描述自行实现，或直接用平台 API / MCP 完成等价动作。

## 前置检查（所有通道共用）
按所选通道检查所需条件，缺了再补齐：

1. **单据定位**：用户已给单据 URL 时接受以下两类；“我的缺陷”或已配置项目的列表采集可按项目及需求作用域解析，不强制用户再给 URL：
   - **单单 URL**（`<缺陷平台>/.../bug/{bug_id}`，常含 project_id）→ 单条模式，分派见下节；URL 自带的 project_id 反哺 config（传 `--project-id` 即持久化）
   - **提测单/需求/view URL** → 列表模式；解析不出需求 ID 时问用户要——猜错范围比多问一句代价大
2. **平台访问能力可用**：能确认当前身份（whoami），且单据读、评论读、状态写三类动作都有授权。失效时使用宿主已有的平台授权通道恢复，不绕过平台客户端直连。
3. **运行依赖**（缺了按下方规则降级，报错时先查这里）：平台客户端 / python3（脚本）/ ffmpeg·ffprobe（视频抽帧，缺则标注「视频证据不可辨」退回文字）/ 目标仓库实际可用的测试入口（按 package scripts / 现有测试文件选择；没有自动化断言时记录验证缺口，不伪造绿灯）。

**与相邻技能的分界**：无工单上下文的崩溃/报错排查走基础 Coding Agent；仅查缺陷平台数据/URL 时使用宿主已有的平台数据能力；缺陷的采集、分析、修复、回写按用户点名的通道分别执行。需求单只是产品设计或实施输入时，不触发本技能。MR 上的 AI 评审意见由 `ai-code-review` 处理，不走本技能。

**多需求防串台**：需求间平级无「当前」概念——config 不存任何需求指针，快照目录 `<req_id>/` 是分析与状态边界。列表采集缺省解析规则为显式 > 唯一快照推导 > 报错列候选。选中具体缺陷进入分析时，必须按缺陷 ID 在已有 `<req_id>/` 的 my-bugs/pending/archive 快照中核实归属；只接受唯一命中，零命中或多命中就询问用户 `req_id`，不能仅凭项目只有一个快照猜归属。后续 dossier、pending、archive 全部归该需求快照；同目录 `code-index` 只承载依赖该需求语境的词义→代码锚点映射。修复/回写读取档案时同样须确定作用域。

## 通道选择（先于一切动作）
按用户意图选通道。每条通道有自己的停止点——在停止点停下是在尊重用户的决策权：用户说「分析」时自动开始改代码，等于替用户决定了「要修」，而修不修、怎么修本该用户拍板。

|用户说什么|走|停止点|
|---|---|---|
|「拉取/更新 buglist」「我的 bug」「重新拉一下」|采集|需求范围三文档、项目范围发现队列落盘即停，不自动分析|
|「分析/归因/根因」+ 指定某条或待分诊|分析|档案落盘 + 格式校验 + pending 同步即停，不自动修复|
|「修/修复/执行」|修复|完成授权修复与验证；真实人工义务未完成时说明并停止|
|「回写/打回/转派/关单/不修」|回写|回写完成即停|
|复合意图（如「拉取并分析」）|按序走用户点名的通道|用户点名的组合执行完即停|

补充三条意图规则：

- **用户指定了档位**（如「挂半自动」）→ 档位按指定值。用户明确给出的决策不需要再确认或重新推导——分析与判据冲突时照用户指定的执行，把冲突点记进档案档位行即可（信息留给用户，判断权也在用户）。
- **用户说「提交/commit」**→ 当前 Git worktree 中已审代码变更直接 commit，不重述方案再问一遍；仅说「修复」不自动提交或回写工单。
- **档位不等于权限**：全自动 / 半自动 / 手动只表示 Agent 的自动化程度，不授予提交代码或修改单据的权限；commit / 回写必须由用户单独点名。

### 单条模式（用户给的是单个缺陷 URL）
bug_id 直接可用，不需要先拉列表。按叠加的意图分派：

|URL 形态|分派|
|---|---|
|单条 URL 单独出现（没说干什么）|采集通道 `--detail <bug_id>` 速查卡片，展示后停|
|单条 URL + 分析意图|`--detail` 获取卡片；先唯一核实或询问 `req_id`，再落 `<project>/<req_id>/analyses/<bug_id>.md`|
|单条 URL + 修复意图|确定 `req_id` 后读取本需求档案；无档案先提示分析该单|
|单条 URL + 回写意图|回写通道直接按 bug_id 走|

列表模式与单条模式可互通：列表卡片里的缺陷就能切单条分析；单条处理完想看全局就拉一次列表。

通道间存在数据依赖（分析吃采集的队列文档，修复吃分析的档案，回写吃终态结论）。前置缺失时提示用户先走对应通道（如「该单无档案，先分析再修」）。

## 产物目录
技能目录只放能力，产物落项目级独立目录（换仓不污染、不随技能分发）：

```
<项目根>/.engineering/issues/
├── config.json    # 多项目配置：owner（whoami 首次解析后缓存）+ projects{pid: app_id}；需求不进 config，两层缺省解析同构（显式 > 唯一推导 > 报错）
└── <project_id>/
    ├── _project/      # my-bugs.md 项目级缺陷发现队列；不进入分析状态机
    ├── <req_id>/      # my-bugs.md / pending.md / archive.md / code-index.md（本需求语境映射）
    │   └── analyses/ # 本需求的分析档案 = 唯一持久分析状态源（存在即已分析）
    ├── media/        # 缺陷截图/录屏（幂等缓存）
    └── evidence/     # 外部补证缓存（需求文档/设计稿/测试用例按源哈希复用；日志原始快照自动落盘）
```

分析档案只有 v2 当前结构；不再兼容旧 v1 模板。档案校验脚本（占位）是 v2 格式硬闸，`--all` 用于批量复检。

从目标项目的 Git worktree 内调用平台客户端。客户端通过 `git rev-parse --show-toplevel` 定位项目根，再进入 `.engineering/issues/`；项目根 `.gitignore` 统一忽略 `.engineering/`。单据保持 issue scope，与 Requirement 只用自然引用关联。

## 通道间通用原则
这些原则跨通道生效，各 reference 里的具体规则都是它们的展开：

- **先读业务上下文**：`.engineering/context.md`（如有）里有业务规则、术语与过去被纠正过的理解，判断“设计如此”还是缺陷时尤其有用。用户纠正了你对业务的理解时，按 `references/workspace-and-ownership.md` 第 9 节写入纠偏记录；只与本需求相关的 QA 用语仍留在本需求的 `code-index.md`。
- **先理解后证据**：能从描述感知到功能模块与具体问题就直接进代码，媒体/外部证据是歧义时的补全手段而非必经站（什么时候看媒体见 analyze.md 证据与定位知识）——跳过理解直接拼凑证据容易把「设计如此」分析成缺陷，但能理解就去抽帧重建理解是本末倒置。
- **结论要能落地**：触点要能定位到行、根因要能解释 QA 的触发路径——解释不了说明归因还没完成，修了也可能是碰运气（具体判据见 analyze.md 调查与停止）。
- **证据先行**：「不修/转后端」必须附证据与置信度——拿不出证据是在把成本转嫁给别人。证据不足时的补证与停止判断见 analyze.md 调查与停止。
- **通用规律才进技能**：只有命中 analyze.md 知识出口的强信号才判断技能规则升维，不要每单主动搜索；候选经验先自问「换一个仓库还成立吗」——成立则反哺进对应 reference，不成立（本次缺陷细节、bug id、拉扯过程）只留档案。此规则只管 Skill references 的通用规则；已验证、昂贵且可复用的 Repo fact 是否回流，独立遵守代码机制缓存的现有 CRUD 与准入，不走知识升维流程。主要输入源：档案质量回写（预判 vs 实际偏差）与 Reopen 质量归因——它们是分析质量/修复质量的直接度量，同类偏差重复出现 = 对应 reference 规则有缺口。
