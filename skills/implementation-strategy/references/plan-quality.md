# 工程风险与验证参考
按当前问题选择有用的领域知识，不要求扫描全部条目或输出固定表格。

## 共享模型的失效位置
新增枚举、状态、档位或配置值时，常见漏点包括 unknown fallback、穷举 switch / map、rank / ordering、窄联合类型、默认分支、布尔压缩、静态矩阵、下一态硬编码、跨服务协议副本与隐式依赖的数组顺序。调查实际消费者与用户可见出口，说明真实漏改后果；可用表、调用链或文字，不固定 Coverage Matrix 字段与位置。

改变共享行为、访问、可见性或约束时，关注可达入口，而不只搜字段名。当前调用方未用的接口、间接返回数据的出口、写侧与旁路同样可能受影响。

## 完整性结论的边界
调查方法由任务决定：调用链、路由、数据流、配置注册或协议闭包均可。只有足够证据支持时才能声称“全部受影响接口 / 所有出口 / 不存在其他路径”；否则描述当前已发现集合与未知，不能据此宣称范围闭合。弱检索、UI 屏蔽和调用方未使用不证明能力不存在。

权限 / 可见性 / 安全控制需验证真实独立访问路径：用户绕开当前入口访问同一能力时，限制是否仍成立。一个 403 不证明其他旁路已受保护；路径数量来自实际结构，不凑用例。

## 风险与可执行验证
高影响风险说明实际后果、处置与如何证明处置有效，不要求绑定 Phase 或固定风险分类。确定性枚举 / resolver 适合参数化测试；跨层行为可能需要集成、runtime 或真实链路证据。普通展示任务不因此强制安全负向用例。

验证条件必须真实可获得：账号、mock / 注入、数据构造、测试环境与外部依赖。mock 或 DOM 代理只证明其覆盖的行为；不能用局部绿灯代替真实交互、视觉或外部系统结果，也不因这些领域名称就自动要求人工。

已有失败与本次回归分开记录；缺失环境如实暴露，只阻塞确实无法成立的结论。已知目标规则、代码处置与验收不能互相矛盾。待决问题只写会改变实现或验证的实际分叉，不用固定类别与五要素表扩写。
